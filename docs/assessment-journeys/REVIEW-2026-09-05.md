1. **`middleware/src/routes/assessment.ts:120-133` (exception creation at
   `middleware/src/providers/assessment.ts:1010-1016`) — a lead-assessor or
   program-lead can approve their own N/A exception; the "never the assessor
   who proposed it" rule is enforced by role, not by identity.**
   The route comment says approval "is a lead-assessor (or above) decision —
   never the assessor who proposed the exception," and `assessor.cedar`
   correctly forbids `assessor` from `ApproveException`. But `lead-assessor`
   and `program-lead` both hold **both** `ScoreAssessment` (can stage an
   `is_na` claim via `POST /teams/:id/scores/apply`, which creates the
   exception row) and `ApproveException` (can approve it) — see
   `middleware/seeds/roles/assessment/lead-assessor.cedar` and
   `program-lead.cedar`. The exception object created at
   `providers/assessment.ts:1010-1016` (`{ dimension_id, status: 'requested',
   source, reason, approved_by: '', approved_at: '' }`) has no
   `requested_by`/proposer field, and `patchException`
   (`assessment.ts:612-651`) never checks one.
   *Failure scenario*: a lead-assessor scores their own team, claims
   `is_na: true` on a dimension (stages a `requested` exception), then calls
   `PATCH /teams/:id/exceptions/:dimensionId` with `status: 'approved'`
   themselves — self-approval succeeds with no record anywhere that the
   approver and proposer were the same person.
   *Fix*: record `requested_by` (from `req.session.sub`) when the exception
   is created, thread it through `applyScores`, and have the PATCH handler
   403/409 when `approved_by === requested_by`.

2. **`middleware/src/routes/identity.ts:41` — the router-level
   `requireAction('ViewIdentityAdmin')` gate blocks program-lead from the
   `ManageUsers` capability the assessment tenant was built to give it,
   making the feature completely unreachable, client and server.**
   `identityRouter.use(requireAction('ViewIdentityAdmin'))` runs before every
   route on the router, including `POST /users` and `PUT /users/:id/grants`
   (both separately gated `requireAction('ManageUsers')`). Only
   `orgiq/hr-admin.cedar` grants `ViewIdentityAdmin`; `program-lead.cedar`
   grants `ManageUsers` but not `ViewIdentityAdmin`. The comment at
   `identity.ts:70-76` (`offendingTenant`) explicitly describes program-lead
   as a scoped, non-admin `ManageUsers` holder whose payload must be checked
   against cross-tenant escalation — i.e. this was built to work for
   program-lead — but the request never reaches that code. The portal
   compounds it: `portal/src/App.tsx:514` wraps `/admin/identity/*` in
   `RequireRole roles={['hr-admin']}` only, so program-lead can't even
   navigate there. `authz-matrix.test.ts` only asserts program-lead "holds"
   `ManageUsers` in the Cedar grant list, never exercises the Express
   middleware chain, so this never surfaced as a test failure.
   *Failure scenario*: a program-lead session calls `POST /api/identity/users`
   to provision an assessor for their own tenant (the documented self-service
   flow) and gets 403 on the router-level check before their `ManageUsers`
   grant is ever consulted.
   *Fix*: grant `ViewIdentityAdmin` to `program-lead`, or split the router so
   `ManageUsers` routes aren't behind the `ViewIdentityAdmin` gate at all
   (leave that gate only in front of the AVP policy/schema routes hr-admin
   uniquely owns).

3. **`middleware/src/providers/assessment.ts:1422-1447` — on the real Aurora
   path, a launched run never transitions out of `status: 'running'`; there
   is no completion write anywhere, so `RUN_CONCURRENCY_CAP` (3) permanently
   exhausts after three runs and `assessment_scoring_logs` never gets written.**
   The mock branch (`assessment.ts:1470-1507`) has a full `setTimeout`
   completion path: it marks the run completed, builds a scoring log,
   applies scores, and publishes `run.completed`. The Aurora branch
   (`!config.mock.aurora`, lines 1422-1447) inserts the run row as `running`
   and returns — nothing analogous exists. Confirmed by grep: the only call
   to `A.updateRunStatus` in the whole file is at `assessment.ts:1565`, on the
   `POST /runs/:runId/stop` path, which sets `status: 'failed'`. There is no
   other route (`routes/assessment.ts` only exposes `GET /runs`,
   `POST /runs`, `GET /runs/:runId`, `POST /runs/:runId/stop`) and
   `assessment-aurora.ts` has no `insertScoringLog`/`upsertScoringLog` at all
   — only read functions (`fetchScoringLogs`/`fetchScoringLog`, lines
   510-524).
   *Failure scenario*: an operator launches `score-dimensions` against a real
   (non-mock) deployment three times; all three rows stay `running` forever
   (no success path exists), `RUN_CONCURRENCY_CAP` is permanently exhausted,
   and every subsequent `POST /runs` 429s until someone manually stops
   (marks failed) each stuck run. `GET /teams/:id/scoring-logs` returns `[]`
   forever in production even though the UI implies scoring is automatic.
   *Fix*: add a completion path (a callback route the agent hits, or a
   poller) that for `SCORE_APPLYING_COMMANDS` calls
   `buildScoringLogForTeam` + `applyScores` + a new `insertScoringLog` +
   `A.updateRunStatus(id, { status: 'completed', ... })`.

4. **`middleware/src/providers/assessment.ts:2158-2205` — `commitSubmissions`'
   Aurora branch computes the next revision/envelope id from an unguarded
   read, with no transaction around the following writes, so two concurrent
   commits for the same team+form either crash on a primary-key collision or
   silently supersede a submission with nothing to replace it.**
   For each selection: `fetchSubmissionsForTeam` (read) →
   `revision = existing.revision + 1` and a deterministic
   `envelopeId = ...-r${revision}` (computed, not DB-assigned) →
   `markSubmissionSuperseded(teamId, existing.envelope_id)` →
   `insertSubmission(envelope, ...)` — three separate round trips, no
   `SELECT ... FOR UPDATE`, no transaction. `envelope_id` is
   `TEXT PRIMARY KEY` (`schema/assessment_schema.sql:147`).
   *Failure scenario A (crash)*: a client retry (network timeout, double
   commit-click bypassing the button's in-flight guard only for a *repeated*
   request) fires two concurrent `commitSubmissions` calls for the same
   team+form; both read the same `existing.revision`, compute the identical
   `envelopeId`, and the second `insertSubmission` throws an uncaught
   unique-violation as a raw 500.
   *Failure scenario B (data loss)*: if `insertSubmission` fails for any
   transient reason *after* `markSubmissionSuperseded` already committed,
   the prior envelope is now permanently `superseded` with no replacement —
   the team's only committed submission for that form silently disappears.
   *Fix*: wrap supersede+insert in one RDS Data API transaction, and make
   revision assignment conflict-safe (e.g. a serial counter or
   `INSERT ... ON CONFLICT (envelope_id) DO NOTHING` with a checked result)
   rather than a client-computed string.

5. **`portal/src/pages/assessment/knowledge/DocPane.tsx:269-280` (broker
   `leave()` at `middleware/src/lib/assessment-broker.ts:175-179`) — a viewer
   can vanish from their own document's presence roster for up to 15s after
   navigating away and immediately back to the same doc, because the tab's
   `leave` and the remount's `enter` are unsequenced fire-and-forget requests
   and `leave` unconditionally deletes by `tab_id`.**
   `getTabId()` (`DocPane.tsx:70-80`) persists the tab id in
   `sessionStorage`, so unmount→remount of `DocPane` for the same `node.id`
   within one browser tab reuses the same `tab_id`. The presence effect
   (`DocPane.tsx:265-277`) sends `enter` on mount and `leave` in cleanup via
   independent `fetch`/`sendBeacon` calls with no ordering guarantee.
   Server-side, `AssessmentBroker.leave(docId, tabId)`
   (`assessment-broker.ts:175-179`) does `doc?.delete(tabId)` unconditionally
   — it has no timestamp/sequence check against a newer `touch`. If the
   stale `leave` request lands after the new `enter`'s `touch`, the viewer's
   entry is deleted and they disappear from their own doc's roster (visible
   to themselves and everyone else) until the next 15s heartbeat re-adds
   them. This reproduces on effectively every doc open under React
   StrictMode's guaranteed mount→unmount→mount in dev, and is a real (if
   less frequent) risk in production under ordinary network jitter or fast
   navigate-away-and-back.
   *Fix*: give each `sendPresence` call a monotonic per-tab sequence number
   and have `leave`/`touch` ignore a request whose sequence is older than
   the last one already applied for that `(docId, tabId)`.

6. **`scripts/validate-assessment-tenant.sh:115-201` — the "journey audit" /
   "role isolation" gates verify only that hand-written markdown files
   contain the right words, not that any check was actually performed
   against a running session.**
   Sections 4 and 4b grep files like
   `docs/assessment-journeys/<role>/<surface>.md` for lines matching
   `^verdict: *pass`, `^console errors: *0`, `^api-status: *403`, etc.
   Nothing in the script drives a browser, calls an API, or diffs against a
   real session's output — a hand-edited or stale markdown file with the
   right field values passes with no assessor/lead-assessor/program-lead
   session ever having been exercised for that run. This sits next to
   otherwise-genuine mechanical checks (tsc/jest/build, component-discipline
   regex counts, the `RequireTenant` grep) in the same script, so a green
   run reads as stronger evidence of tenant isolation than it is.
   *Fix*: require a machine-generated artifact (timestamp + response-body
   hash from an actual curl/Playwright run against each role) instead of
   freeform markdown the script only pattern-matches.

7. **`middleware/src/lib/assessment-broker.ts:41,83-84,111-114` — the 500-slot
   SSE replay buffer is one process-wide ring shared across every doc and
   run in the tenant, so `replay()` cannot distinguish "you're fully caught
   up" from "the buffer didn't go back far enough," and busy activity on
   *other* docs/runs evicts a reconnecting client's own missed events sooner
   than expected.**
   `AssessmentBroker` is a single exported instance
   (`export const assessmentBroker = new AssessmentBroker()`) with one
   `buffer` array backing presence, knowledge saves/comments, and
   `run.progress` for all docs/runs tenant-wide. `replay(afterSeq)`
   (lines 111-114) just filters `seq > afterSeq`; if the client's last seen
   seq is older than the oldest entry still held (already evicted by the
   `shift()` at line 84), the filter returns everything currently buffered —
   indistinguishable from "nothing missed." This is called out in the code's
   own comments as an intentional "best effort" tradeoff mirroring
   `canary-broker.ts`, so it is a known design choice, not an oversight —
   but scoping the buffer per-broker rather than per-resource means an
   unrelated flurry of events on other docs/runs can silently blow the
   retention window for a client that only cares about one doc.
   *Failure scenario*: a user's laptop sleeps while other teams generate
   >500 combined events elsewhere in the tenant; on wake, their `EventSource`
   reconnects with its old `Last-Event-ID`, gets a full-but-gapped replay,
   and the UI shows "Live"/up to date while some of that user's own missed
   events (a comment, a save, a presence change) are gone with no
   indication.
   *Fix*: scope the ring buffer per `doc_id`/`run_id`, or have `replay()`
   return a flag when `afterSeq` predates the buffer's oldest entry so the
   route/client can render a "some updates may be missing, reload" notice.

8. **`schema/assessment_schema.sql:146-159` — `assessment_submissions` has no
   foreign key or uniqueness constraint backing the "one committed envelope
   supersedes the last" invariant that finding #4's application code
   depends on entirely.**
   Every other cross-table reference in this schema
   (`team_id`, `run_id`, `doc_id`, etc.) is declared
   `REFERENCES ... ON DELETE ...`; `supersedes TEXT` (line 151) is not, so it
   can point at a deleted or nonexistent envelope with no integrity check,
   and nothing at the DB level enforces at most one `committed` row per
   team+form. That invariant lives entirely in the non-atomic application
   logic described in finding #4.
   *Fix*: add `supersedes TEXT REFERENCES assessment_submissions(envelope_id)`
   (nullable), and once a real form-id column exists (today it's only inside
   the `envelope` JSONB), a partial unique index on
   `(team_id, form_submission_id) WHERE status = 'committed'`.

9. **`middleware/src/lib/sse.ts` — `initSSE` clears its heartbeat interval on
   the response's `'close'` event but registers no `'error'` listener on
   `res`, so a socket reset mid-write can crash the whole middleware
   process.**
   If the underlying socket resets while a `res.write()` is in flight (the
   25s heartbeat tick, or a `writeSSE` call) before `'close'` fires, Node's
   `Writable` emits `'error'` on the response object; with zero listeners
   registered, an `EventEmitter` with no `'error'` handler throws, which is
   an uncaught exception at the process level. This pattern predates
   tonight (shared with `canary.ts`'s use of the same `initSSE`), but the
   assessment tenant's `/events` route adds a second, longer-lived class of
   SSE consumers riding the same unguarded path, raising how often it's
   exercised. Not reproduced here (would require simulating a mid-write
   socket reset) — flagging as a real, verified gap in the code, not a
   confirmed crash in practice.
   *Fix*: add `res.on('error', () => clearInterval(heartbeat))` alongside
   the existing `'close'` handler in `initSSE`.

10. **`middleware/src/providers/assessment-aurora.ts:503-524` —
    `rowToScoringLog` and its two SELECTs never fetch `run_id`, even though
    `assessment_scoring_logs.run_id` exists in the schema
    (`schema/assessment_schema.sql:189`) and `M.ScoringLog.run_id` is a
    defined field.**
    Harmless today only because nothing on the Aurora path ever inserts a
    scoring log (see finding #3), so `fetchScoringLogs`/`fetchScoringLog`
    have nothing with a `run_id` to lose yet. It will silently drop
    `run_id` from every log the moment #3 is fixed, unless this SELECT is
    updated at the same time.
    *Fix*: add `run_id` to both SELECTs and to `rowToScoringLog`'s mapping
    when the completion path (#3) is implemented.

### `deriveTeamStatus` (`middleware/src/mock/assessment.ts:2126-2133`) — correct, with one reachable oddity

The function is a clean pure fold: nothing touched → `NEW`; some but not all
applicable dimensions carrying a level → `IN_PROGRESS`; every applicable one
scored → `ASSESSED`. A missing score object is treated as applicable-but-
unscored (`!s?.is_na` is true for `undefined`, and `assessed` requires
`s != null`), which is the right way round — an absent dimension holds a team
in `IN_PROGRESS` rather than letting it graduate. Verified live across the
whole roster, which now shows three distinct states rather than the single
stuck value the journey logs used to record: TEAM-001 `ASSESSED`, TEAM-002
`ASSESSED`, TEAM-003 `IN_PROGRESS`, TEAM-004 `IN_PROGRESS`, TEAM-005
`IN_PROGRESS`, TEAM-006 `NEW`, TEAM-007 `NEW` — and TEAM-006/TEAM-007 were
watched moving to `ASSESSED` as their submissions were processed, while
TEAM-005 correctly stopped at `IN_PROGRESS` on 16 of 17.

The oddity: a team whose every dimension carries an approved N/A exception
has `applicable.length === 0`, so `assessed.length >= applicable.length` is
`0 >= 0` and the team reads `ASSESSED` while its scorecard reads 0/17. Not
reachable from the seed data and arguably the right answer ("nothing applies
to this team, so it is done"), but the pill and the count will disagree if
anyone ever gets there. Worth a one-line guard or a distinct label rather
than a fix.

### `isSubmissionProcessed` (`middleware/src/mock/assessment.ts:6013-6026`) — the predicate is stricter than its name

This is the one substantive finding of the re-review, and it is filed as an
Open defect against lead-assessor, program-lead and admin. The projection
asks, for every dimension a committed envelope hinted at, that
`score.current_level !== null || score.is_na` **and** that
`score.updated_at >= env.ingested_at`. The recency half is right and guards
a real case (a resubmission must not read as processed because older scores
happen to cover the same dimension ids). The first half is not "was this
processed", it is "did processing produce a verified level", and those come
apart: a run that reads the evidence and concludes "documented, pending
verification" writes `current_level: null` with
`certification.status: 'pending'`, which is a successful outcome the
predicate reads as not-scored.

Reproduced three times across three roles and three revisions of TEAM-005's
Form #7, with the evidence link marked fetched, skipped, and marked fetched
again. Each run reported "Completed — Scored 17 dimensions: 5 from evidence,
12 low-confidence with no evidence; 12 follow-ups opened" and the list kept
the amber "Unprocessed" pill. The perverse consequence is visible in the same
batch: the two submissions with **no** evidence link (TEAM-006, TEAM-007) got
a self-attested level and flipped to "Processed", so attaching evidence makes
a submission less likely to be marked processed, and this row can never leave
the UNPROCESSED count however many times it is run. Either the predicate
should accept "scored, level pending", or the list needs a third state.

### `resolveTeamName` (`portal/src/pages/assessment/secondaryFormat.ts:163-172`) — correct, and the one race is not observable

The function is small and right: look the id up in the roster, fall back to
the submitted text when there is no match, and keep the submitted text as
secondary only when it genuinely differs case- and whitespace-insensitively.
The risk worth checking is the empty-map default (`groupSubmissions`'s

## A1. The self-save banner suppression loses a race it was written to win — and never retracts

`DocPane.tsx:228-230,271-284` has a deliberate mechanism for telling "the SSE
echo of my own save" apart from "someone else changed this doc": `handleSave`
stores the PUT's `result.updated_at` in `mySavedTs`, and `externalDocSave`
(`knowledgeFormat.ts:507-517`) drops any `knowledge.doc.saved` whose `ts` is
`<= ignoreUpToTs`. The server cooperates exactly as intended — `putKnowledgeDoc`
(`middleware/src/providers/assessment.ts:2589,2601`) publishes the event with
the *same* string it returns as `updated_at`, so the comparison is sound.

It still fires on the saving tab. Observed four times this pass, once per
role: immediately after Save the originating tab shows "Updated by u-jonas
just now" with a **Reload** action, alongside its own "Saved." banner.

Two defects, one root:

1. **Ordering.** `assessmentBroker.publish(...)` runs inside the PUT handler,
   so the SSE frame is on the wire before the handler returns. The client's
   `setMySavedTs(result.updated_at)` runs only after `putJson` resolves. In
   between, the notice effect can run with `mySavedTs === null`, treat the
   event as external, stamp `seenExternalTsRef.current`, and call `setNotice`.
2. **No retraction.** When `mySavedTs` does land the effect re-runs,
   `externalDocSave` correctly returns `null` — and the effect returns early
   without clearing the notice it set a tick earlier. The guard is
   write-only: it can suppress a notice it has not yet shown, never withdraw
   one it has.

There is a third, simpler path to the same wrong banner: reload the saving
tab. `mySavedTs` resets to `null` on mount while the SSE backlog still
carries the save, so the tab is told about its own change on a fresh load —
which is what makes the banner look sticky (observed surviving a full reload,
and still reading "just now" minutes later when another role opened the page).

Fix direction: record the intent, not the result — set a "my save is in
flight" marker before the PUT (a monotonic local counter, or the actor's own
`sub` compared against `e.by` for events within a short window), and have the
effect clear `notice` when `externalDocSave` returns `null`. The `by` field is
already on the event and already carries the actor's sub, so comparing it to
the session's own `sub` would close all three paths including the reload one.
Filed as lead-assessor/DEFECTS.md Open #6 (also in program-lead's and
admin's).

## A2. `isSubmissionProcessed` can be satisfied by scoring that has nothing to do with the submission

The new predicate (`middleware/src/mock/assessment.ts:6027-6039`) is a real
improvement — "was a scoring pass recorded" is the right question, and the
old `current_level !== null || is_na` genuinely conflated "never looked at"
with "looked at, concluded not enough evidence". The recency clause
(`entry.changed_at >= env.ingested_at`) also correctly stops a fresh revision
inheriting an older team's history. But dimension scores are team-scoped and
the history entries carry no submission id, so the test is "this team's
dimension was scored at some point after this envelope arrived" — not "scored
*because of* this envelope".

Consequences, in increasing order of how likely they are to bite:

- A team with two open submissions: processing the newer one writes history
  for the shared dimension ids and flips the older one to "Processed" too,
  without it ever having been run.
- An assessor hand-scoring a dimension on the scorecard right after an
  intake lands marks that intake processed.
- The reverse is safe: nothing here can make a genuinely-processed
  submission read Unprocessed, so this is a false-positive risk on a status
  chip, not a data-integrity one.

Not a regression — the old predicate had exactly the same team-scoping — and
not worth reverting the fix over. But if the status is ever going to drive
something more than a pill and a counter, the honest shape is a submission id
(or the run id) on the `history` entry that `applyScores` appends, and a
predicate that matches on it. Worth a line in the code comment at minimum;
the current comment explains the recency check but not this limit.

## A3. `unknown_team` short-circuits duplicate detection, so a hand-matched row can never be "Seen"

## NEW: the run-complete exemption regex is stricter than the route it exempts

This is the one substantive finding of the pass, and it is a direct consequence
of the consolidation's shape rather than of the compare it moved.

The tenant gate now lives inside the router so the agent callback can be
exempted from it (`routes/assessment.ts:65-70`):

```
const RUN_COMPLETE_PATH = /^\/runs\/[^/]+\/complete$/;
assessmentRouter.use((req, res, next) => {
  if (req.method === 'POST' && RUN_COMPLETE_PATH.test(req.path)) { next(); return; }
  requireTenant('assessment')(req, res, next);
});
```

That hand-written matcher is a **second, stricter** copy of the route's own
matcher, and Express's is not an anchored regex. Express defaults to
`strict: false` and `caseSensitive: false`, so `POST /runs/:runId/complete`
also serves `/runs/<id>/complete/` and `/runs/<id>/COMPLETE` — neither of which
this regex matches. Exercised, sessionless, against the running middleware:

| request | result |
|---|---|
| `POST /api/assessment/runs/does-not-exist/complete` | **404** — reached the handler; the gate was skipped, as intended |
| `POST /api/assessment/runs/does-not-exist/complete/` | **403** `{"error":"Forbidden","requiredTenant":"assessment","tenant":"orgiq"}` |
| `POST /api/assessment/runs/does-not-exist/COMPLETE` | **403**, same body |

So a caller whose path differs from the exemption only in a trailing slash or
in case is refused by the tenant gate on a route Express would otherwise have
routed to the exempt handler. The failure is worse than the code it replaced in
one specific way: the 403 body reads as a **tenant** problem
(`requiredTenant: assessment, tenant: orgiq`), which is the least useful thing
to hand a machine caller that has no tenant at all and whose real problem is
path spelling. `agents/_shared/callbacks.py` builds the URL itself today and
gets it right, so nothing is broken in practice — but a proxy that normalises
trailing slashes, or a future caller built from a base URL that ends in `/`,
turns a working callback into an unexplained 403.

*Fix direction*: stop maintaining a second matcher. Either mount the callback
on its own `Router` ahead of the tenant-gated one (Express then does the
matching once, with its own rules), or normalise before testing — strip one
trailing slash and lower-case — so the exemption cannot be narrower than the
route. The first is better: it removes the class rather than this instance.

# Finding 7 — CLOSED, 2026-09-08: the SSE replay ring is partitioned

Carried open across four passes ("still open, unchanged by this work" three
times in a row). It is closed now, at the wire, and this is what was done.

## The key: `<channel>:<resource-id>`

`lib/assessment-broker.ts` no longer holds one 500-slot array. Retention is a
`Map<partitionKey, ring>` where the key is built by `partitionKeyFor(event)`:

    knowledge.presence           -> presence:<doc_id>
    knowledge.doc.saved          -> doc:<id>
    knowledge.published          -> doc:<id>
    knowledge.comment.created    -> doc:<doc_id>
    knowledge.pulled             -> pull:<section>
    run.progress                 -> run-progress:<run_id>
    run.started/completed/failed -> run:<run_id>

The review's own prescription was "per `doc_id`/`run_id`", and a resource-only
key would NOT have fixed the reported failure: presence and saves are both
doc-scoped, so `presence` for doc D and `doc.saved` for doc D would have gone
on sharing one FIFO and the loud one would still evict the quiet one on the
doc anyone actually cares about. The channel segment is what separates
*cadence classes*; the resource segment is what stops one hot doc/run/section
starving another. Both are load-bearing.

The channel also decides the retention SHAPE. `presence` and `run-progress`
are full-state snapshots — the portal reads only the newest of each
(`presenceForDoc`, `applyRunEvent` in `portal/src/pages/assessment/knowledge/`)
— so they are `superseding`: capacity 1, and in-place supersession is the one
drop that does not raise the gap watermark, because the entry that displaced
it has a higher seq, describes the same resource, and lands in the same
replay. `doc` (64), `run` (16) and `pull` (32) keep real history.

## Every property the old design had, kept

- Fresh connection (no `Last-Event-ID`) still replays nothing and is never
  gapped. `decideReplay`'s first branch is untouched.
- A reconnect is still bounded by `REPLAY_MAX_AGE_MS` (30 min); anything older
  is withheld and gaps.
- `stream.gap` is still emitted for every real loss, and this was the part that
  needed care: the old eviction test was `afterSeq < oldest - 1`, which is only
  sound on a CONTIGUOUS ring. Partitioning gives contiguity up, so the store
  keeps one monotonic watermark, `droppedThroughSeq` — the highest seq it has
  discarded in a client-visible way — and `decideReplay` gaps exactly when
  `afterSeq < droppedThroughSeq`. That is O(1), exact rather than heuristic,
  and it is why partitioning did not quietly replace an honest signal with
  silence. Verified live below, in both directions.

## How a key is retired, and why that is safe

1. **Age, primary.** Every push sweeps entries older than `REPLAY_MAX_AGE_MS`
   and deletes any partition left empty. Safe because `decideReplay` already
   refuses to deliver anything past that bound: a partition whose newest entry
   has aged out cannot contribute one frame to any future replay, so retiring
   it costs a client nothing it could have received. The dropped seqs DO raise
   the watermark, because with the events still held `decideReplay`'s `agedOut`
   branch would have gapped exactly the same clients — the watermark reproduces
   the pre-existing signal rather than suppressing it.
2. **LRU cap, backstop.** `MAX_PARTITIONS = 256`; the least-recently-published
   key goes first and its remaining events raise the watermark, so anyone who
   needed one is told `stream.gap`. Age retirement alone bounds the map only if
   resource ids are reused; this covers a burst of distinct ids inside one
   window.

Worst case retained is `MAX_PARTITIONS x` the largest capacity = 256 x 64 =
16,384 small objects, and only if every partition were a saturated `doc:` ring.
Steady state is "what was published in the last 30 minutes", which on this
tenant is far below the old flat 500.

## Tenancy: the key carries no tenant segment, deliberately

Every event on this broker is an assessment-tenant event by construction — the
only publishers are `providers/assessment.ts`, the only reader is
`assessmentRouter`, which is mounted behind `requireTenant('assessment')`. A
tenant segment would be a constant. It would also be security theatre: the SSE
stream is not filtered per subscriber, every subscriber on the route already
sees every event on the broker, and partitioning RETENTION cannot change that —
`requireTenant` is what keeps another tenant off the route. (The earlier note
that the ring is "process-wide across tenants" is, on inspection, process-wide
across *resources*; there is one tenant here.) If a second tenant is ever
published onto this broker, `partitionKeyFor` is the single place to prepend
the tenant, and the resource ids would have to be made tenant-unique at the
same time.
