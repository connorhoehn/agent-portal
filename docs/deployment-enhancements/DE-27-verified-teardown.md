## Current state (read from the code, 2026-10-27)

The backlog line is partly stale. `infra/scripts/destroy.sh` already verifies
against the API, refuses the success banner on a failed stack listing, and
sweeps billing resources by their own APIs (`destroy.sh:660-843`, from
`a0cd33fa` and later). The memory "destroy.sh has reported success through
expired credentials" describes the version before that (`:44-46` records it).
What is left are three narrower holes.

- **An API error mid-sweep still reads as "no survivor".** The sweep checks
  credentials once (`:703`), then every query is `2>/dev/null || true`
  (`:716-829`). A token that expires after `:703`, an `AccessDenied` on one
  service, or throttling returns empty output, and empty output is "clean".
  That is the same false success, moved from the stack list to the sweep. The
  PURGE section has the same shape: the secret and SSM deletes (`:563-568`)
  add nothing to `FAILURES` when they fail.
- **Survivors it never looks for.** Compared with what the stacks retain or
  scripts create:

## Change

1. **An account guard first.** `EXPECTED_ACCOUNT` (default `647757222309`,
   overridable by env or `--context`, for DE-17's other environments). Both
   scripts exit 2 before any write if `sts get-caller-identity` returns a
   different account.
2. **A checked query helper.** Replace `cmd 2>/dev/null || true` in the sweep
   with `sweep_query <label> <aws args…>`: it captures stderr, and on a
   non-zero exit appends `"<label>: unverified (<first line of error>)"` to
   `FAILURES` and returns empty. A `NotFound` style error (already gone) is
   the one exit code treated as empty, matched per service. The PURGE deletes
   use the same helper, so a failed purge is reported.
3. **A declared inventory.** `infra/scripts/teardown-inventory.sh` (sourced by
   `destroy.sh` and DE-26's `burn.sh`) lists each survivor class as one line:
   label, list command, filter, whether PURGE deletes it. The sweep iterates it.
   Add the rows from the table above, and drop the OpenSearch row.
4. **A tag-based backstop.** Once DE-26 tags every stack with `orgiq:env`,
   `aws resourcegroupstaggingapi get-resources --tag-filters Key=orgiq:env,Values=<env>`
   lists anything tagged that the inventory missed. Report each ARN as
   "untyped survivor". The tagging API covers most but not all resource types
   and can list recently deleted ARNs for a while (unverified per type), so it
   reports, never fails the run on its own.
5. **A machine-readable result.** `destroy.sh --report <file>` writes JSON:
   `{ account, region, stacksRemaining[], survivors[{label,id}], unverified[] }`,
   so DE-14's orchestrator and a human read the same thing.

## Decisions owed

- **Is an untyped tagged survivor a failure?** Proposal: a warning, until the
  tagging API has been checked against one real teardown.
