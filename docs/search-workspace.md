# Search workspace

`/iq/search` combines Results, Answer, and Connections under one mounted conversation. The Org sidebar links to Search. Legacy `/search`, `/invoke`, `/iq/invoke`, `/explore`, `/graph`, and `/iq/explore` links retain their parameters and select the appropriate view.

The URL carries `q`, `type`, optional initiative `scope`, `tab`, pagination `offset`, `selection` and attached `context` as typed record keys, graph `layout`/`graphType`, and the existing conversation `session`. Results and graph selections use original identifiers. Selecting a record never changes its source. Designs remain initiative-linked design threads; publishing knowledge does not authorize execution.

The composer is the shared `AgentComposerDock` from ui-components — the same shell as the initiative pages (`InitiativeComposer.tsx`), in its `document` presentation: the Agent ⌄ mode menu (Chat and Terminal listed but off, each with its reason), the attached records as removable context chips, the B I code link attach strip, a Workflow ⌄ menu, `/ commands` and Send. `#` looks up records as context, and `/agent <name or ID> <question>` picks an agent explicitly; ordinary questions use the supervisor's existing routing, and explicit agent requests use the same tenant and capability gates as all other invocations. The Workflow ⌄ rows are the `searchWorkflows` prompt templates (`pages/search/searchWorkflows.ts`: Who can help, Explain the selection, Summarize results) over the current query, scope and selection — the same rows are the `/ commands`, a row that does not apply is disabled with its reason, and picking one puts its prompt in the draft. Attachments follow the shared shell: files stay in the draft and are not forwarded to the agent (as on the initiative composer).

`GET /api/search` searches existing providers, returns permission-filtered counts, records, and verified edges, and reports partial or bounded source reads. Every initiative in the source window is scored on its summary, read for all of them in one batch, so a scope can narrow results but never add a summary match the workspace search misses; per-initiative detail reads stay bounded to the scoped or name-matched initiatives and load only contributor edges. `sort` is `relevance` (the default, score order) or `recent`; anything else is a 400. `recent` orders by each record's `updatedAt`, newest first, puts records without one after every dated record, and breaks ties by relevance. `updatedAt` is ISO and appears only where the source records a time: an initiative's last activity (else its creation), a work item's or approved design's `updatedAt`, a decision's `decidedAt`, an observation's `created_at`, a pattern's or guide's `updated_at`, and an agent-library asset's `updatedAt`. People carry none, and none is ever invented. Each scored record carries `matchReason`, the part of scoring that set its rank, verbatim one of: `Title match`, `Text match` (description or subtitle only), `Matched through initiative membership` (a person linked by owns/SME/contributes to an initiative the query names), `Matched through initiative work` (work an initiative the query names includes), `Matched through a linked initiative` (any other record linked to that initiative), and `In scope` (scoped browsing with no query); with no query and no scope it is absent. `highlights` lists the query terms, after stopwords, that occur in the record's title, description or subtitle, in query order without duplicates; it is `[]` for a record matched only through an edge and absent when there is no query. Unscored related records carry neither field. `GET /api/search/records?keys=type:id,...` resolves selected records separately from the result page. The initial graph focuses the most relevant records; Show all expands it. Search is a bounded read model over existing providers, not a new semantic index.

Server-resolved context is emitted as a numbered `search_context` tool result and stored with the assistant turn. Inline citations, record rows, source links, and restored graph relationships use that observed metadata. Unsupported or truncated references are not turned into evidence. Context is untrusted data and grants no additional runtime permission.

Saved searches use `/api/saved-searches` CRUD and belong to the authenticated user and tenant. They store query/view/filter/selection state, not copied records or transcripts. Production deployments must apply `schema/search_workspace_schema.sql` (registered with `load_schema.py`). Mock mode follows the existing in-memory provider convention. Recent conversations continue to use AgentCore Memory; missing memory is displayed explicitly.

Verification covers query and selection persistence across views, legacy links, typed context, source restoration, saved-search ownership and CRUD, graph keyboard selection/layouts, automatic versus explicit agent routing, and composer/rail layout at desktop widths.
