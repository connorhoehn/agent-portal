# The voice navigator: talk your way through the portal

Design for the thing the owner asked for on 8 November 2026: a voice assistant picked up from the bottom toolbar that moves through the apps ("open search", "find me the latest kubernetes experts", "open the computer lab and start a VM in each of my active projects", "has there been any issues with any of the bot sweeps since yesterday", "send a message to the X team that I'm out today and set my status", "open the access tenant and see if my request got approved"), with a visible indication that it is live. Written from the prototype in `chatgpt-live-voice/` and the code named below; nothing here is built.

Tags: **fact** = read in this repository (file named); **fact (OpenAI)** = read in the prototype's own code or README; **fact (OpenAI, verified 8 November 2026)** = observed against the real Live API by `scripts/voice/probe-realtime.mjs` (package V1), raw events in `docs/voice/live-events.jsonl`; **fact (OpenAI docs)** = read in OpenAI's Live API reference or guides (developers.openai.com, `/api/reference/resources/live`, `/api/docs/guides/live-delegation`) and not exercised by the probe; **unverified** = reported but not confirmed (none left after V1); **decision** = a choice this design makes.

## 1. What exists today

### The prototype

- `chatgpt-live-voice/` is untracked: `index.html` (one page), `server.mjs` (dependency-free Node), `README.md`, `.env` with the key. **fact**
- Transport. The browser creates an `RTCPeerConnection` with the microphone track and an `oai-events` data channel, posts the SDP offer to the local server's `/api/session`, which forwards `{ session, transport: { type: 'webrtc', sdp } }` to `POST /v1/live/sessions` with the API key and returns the answer. The key never reaches the browser. **fact (OpenAI)** (`server.mjs:102-126`, `index.html:378-418`)
- Session object. `model` (`LIVE_MODEL`, default `gpt-live-1`), `instructions` (capped at 20,000 characters), `audio.output.voice` (built-in name or a `voice_…` id), and when `LIVE_DELEGATION_MODEL` is set, `delegation: { type: 'responses', responses: { model, tools: [{ type: 'web_search' }], tool_choice: 'auto' } }`. **fact (OpenAI)** (`server.mjs:106-121`)
- Events the page handles on the data channel: `session.started`, `session.input_transcript.delta` (you), `session.output_transcript.delta` (assistant), `session.usage.updated` (`usage.seconds`), `session.input_audio.muted/unmuted`, `session.closed` (final usage), `error`. The page sends `session.close`, `session.input_audio.mute/unmute` and `session.commentary.append { delegation_id: null, content }` ("inject" box). **fact (OpenAI)** (`index.html:329-358,422-468`)
- Hang-up. `session.close` then wait for `session.closed`; if the channel dies, `POST /api/hangup` calls `/v1/live/sessions/{id}/hangup` so the session stops billing. **fact (OpenAI)** (`server.mjs:128-136`, `index.html:422-450`)
- Level meter. A `WebAudio` analyser on the microphone stream drives a width percentage every animation frame. **fact (OpenAI)** (`index.html:294-308`)
- Cost. The README quotes about $0.05 per minute of voice, billed per second, with a 15-second minimum per WebRTC session; the page's figure uses that rate and calls it an estimate. **fact (OpenAI)** (`README.md`)
- Function calls. The prototype defines no functions; `web_search` is the only delegated tool. What the Live API does with functions, measured in V1, is the next subsection. **fact (OpenAI)** (`server.mjs:115-120`)

### The Live API, as V1 measured it

Six probe sessions on 8 November 2026 (UTC) with the key in `chatgpt-live-voice/.env`: `gpt-live-1` for the voice, `gpt-6-luna` for delegation (`LIVE_DELEGATION_MODEL` is unset in `.env`; the account also lists `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-6-sol`), test speech from the Qwen3 `male` voice streamed as 24 kHz PCM16 in real-time 100 ms chunks. Each line below is **fact (OpenAI, verified 8 November 2026)** unless tagged otherwise; the session label in brackets is the `s` field in `docs/voice/live-events.jsonl`.

- Endpoint. The Live API is its own surface, not the Realtime API. Primary WebSocket `wss://api.openai.com/v1/live/sessions` with no query parameters, `Authorization: Bearer <key>`, no `OpenAI-Beta` header; the first message is `session.start { event_id, session }` and the answer `session.started { client_event_id, session: { id: 'live_u0_…', expires_at, model, instructions, audio, delegation, status: 'active', input: [], client? } }` echoes the resolved configuration. The Realtime URL refuses the model: `wss://api.openai.com/v1/realtime?model=gpt-live-1` answers `error { code: 'invalid_model', message: 'Model "gpt-live-1" is not supported in realtime mode.' }`. None of the Realtime names apply (`session.update` with tools, `input_audio_buffer.append`/`commit`, `conversation.item.create`); audio is `session.input_audio.append { audio: <base64 raw PCM> }` with no commit and no acknowledgement, and turn-taking is the model's own (no VAD settings exist). [`realtime-handshake`, `live-responses`]
- Session shape for tools. Functions go in `session.delegation.responses.tools` as Responses function tools: `delegation: { type: 'responses', responses: { model: 'gpt-6-luna', instructions: <backend prompt>, tools: [{ type: 'function', name, description, parameters: <JSON schema>, strict: true }], tool_choice: 'auto', parallel_tool_calls: false } }`. Strict schemas with `enum` and `additionalProperties: false` are accepted and honoured (`navigate` was called with `{"route":"/iq/local-compute"}` from the enum). A plain `session.tools` array is refused before the session starts, so nothing is billed: `error { code: 'unknown_parameter', param: 'session.tools', message: "Unknown parameter: 'session.tools'." }`. The audio format for a WebSocket is `session.audio.format: { type: 'audio/pcm', rate: 24000 }`; WebRTC negotiates its own. [`live-plain-tools`, `live-responses`]
- Inbound tool call. "Find me the latest Kubernetes experts." produced, in order: `session.delegation.created { offset_ms, delegation: { id: 'item_…', type: 'delegation', target: 'responses', response_id: 'resp_…' } }` 100 ms after the last input transcript delta; then `response.event { delegation_id: 'item_…', event: { … } }` envelopes carrying nested `response.created`, `response.in_progress`, `response.output_item.added` (the item with `status: 'in_progress'`, `arguments: ''`), `response.function_call_arguments.delta` ×7, `response.function_call_arguments.done { item_id, arguments }` (no `call_id` or `name`), and `response.output_item.done { item: { id: 'fc_…', type: 'function_call', status: 'completed', call_id: 'call_…', name: 'search_people', arguments: '{"query":"Kubernetes experts"}' }, output_index, sequence_number }`, 1.1 s after the delegation. Then `response.completed` arrives before any result is sent, with `response.output: []`, `tools: []`, `instructions: null` and the backend token `usage`; it is not a "done" signal for the call. "Open the computer lab." gave `navigate { route: '/iq/local-compute' }` 0.5 s after its delegation. "Hey, I want to do search." delegated nothing: the voice answered "No problem. What do you want to search for?" itself. [`live-responses`]
- Outbound result. `response.item.create { event_id, item: { type: 'function_call_output', call_id, output: '<JSON string>' } }` then `response.create { event_id }`; item.create has no acknowledgement. The continuation is a new nested response (`response.created` 145 ms later, new `resp_…` id, same outer `delegation_id`) whose `response.output_text.delta` stream the voice paraphrases aloud; its first spoken transcript delta came 440–650 ms after that response's `response.completed`. [`live-responses`]
- Talking while the tool runs. The voice speaks one short acknowledgement the moment it delegates, overlapping the backend's call ("Sure, I'll look that up.", "Okay."; in client mode "Okay, let's get that opened up." and "I'll get that going."), then stays silent until the result arrives. It never filled the wait: with a 3-second tool delay the session timeline shows 4.6 s and 5.0 s of silence between the acknowledgement and the spoken result; in client mode with a 5-second delay every voiced frame fell in the first 1.6 s of the wait (13 frames) and the first 1.0 s of the second (7 frames). Output audio `session.output_audio.delta { delta }` streams continuously in 100 ms frames (4,800 bytes at 24 kHz) including silence, so "speaking" can only be read from `session.output_transcript.delta` or audio energy, never from frames arriving. [`live-responses`, `live-client`]
- Thinking. There is no thinking event. Between the user's last `session.input_transcript.delta` and the first `session.output_transcript.delta` or `session.delegation.created`, only silent output-audio frames arrived (100–314 ms in all three turns). Transcript deltas carry `start_ms`/`end_ms` on the session timeline in 200 ms steps. [`live-responses`]
- Mid-session context, all on the same socket with `delegation_id: null` under Responses delegation: `session.thinking.append { content }` → `session.thinking.appended { start_ms, end_ms, client_event_id }`; `session.instructions.append` → `session.instructions.appended`; `session.commentary.append` → `session.commentary.appended`; each acknowledged about 630 ms later. Commentary is spoken ("The Computer Lab page is open now. Two computers are currently running."), and the appended instruction took effect in the same reply ("Do you need help with anything else?"). A non-null `delegation_id` under Responses delegation is refused: `error { message: 'Unknown client or Decision delegation.', param: 'delegation_id' }`. [`live-responses`]
- Client delegation. `delegation: { type: 'client' }` gives `session.delegation.created { delegation: { id, type: 'delegation', target: 'client' } }` with no `response_id`, no task text and no arguments. The application answers with `session.commentary.append { delegation_id, content }` (→ `session.commentary.appended`), which the voice speaks; the follow-up "Yes." opened a second delegation. This mode gives no structured arguments, so the catalogue in §4 needs Responses delegation. [`live-client`]
- Mint (what P2 proxies). `POST /v1/live/sessions { session: { model, instructions, audio: { output: { voice } }, delegation, client? }, transport: { type: 'webrtc', sdp: <offer> } }` → `201 { session: { id: 'live_u0_…' }, transport: { type: 'webrtc', sdp: <answer> } }`, exactly the prototype's flow. There is no ephemeral `client_secret` in the Live API: the server exchanges the SDP and the browser never holds a credential. `POST /v1/live/sessions/{id}/hangup` → `200 {}` (body empty), and works on a session whose media never connected; that session ended `session.closed { reason: 'close_requested', usage: { seconds: 15 } }` after 3.4 s, so the 15-second minimum is real. [`mint-webrtc`]
- Data-channel permissions. The mint accepts `session.client.data_channel: { allowed_client_events: [<event names>], allowed_server_events: [{ type }, { type: 'response.event', response_event: <nested type> }] }` and echoes it in `session.started`. [`mint-webrtc`] Without it the browser's data channel may send every client event, including `session.update`, which can replace `delegation.responses` (model, tools, backend instructions) mid-session. **fact (OpenAI docs)** (reference `ClientConfig`, `SessionUpdateEvent`)
- Sideband. `wss://api.openai.com/v1/live/sessions/{id}/attach` with the API key attaches to a minted WebRTC session at once (before media connects), receives `session.started` with the full resolved configuration and `session.closed` with final usage. [`mint-webrtc`]
- HTTPS beyond the socket. On a WebSocket nothing else is needed: start, audio, tool results, context and close all ride the socket. With WebRTC the only HTTPS calls are the server's mint and hangup. Tool results are the client events `response.item.create` and `response.create`, which the server accepted in the data-channel allowlist [`mint-webrtc`]; V1 could not send them over a live data channel (Node has no WebRTC stack); the 8 November browser walk did, and both were accepted (next subsection).
- Usage. `session.usage.updated { usage: { seconds }, context_window: { usage_ratio } }` and `session.closed { reason, usage: { seconds } }` are cumulative (56 s for the 51-second main session, 23 s for the client session). Delegated tokens are billed separately and appear only in nested `response.completed.response.usage { input_tokens, input_tokens_details: { cached_tokens, cache_write_tokens }, output_tokens }`: 1,060 in and 20 out for the search call, then 1,194 and 28 for its continuation, with prompt caching on later turns. The snapshot also shows `gpt-6-luna` running at `reasoning.effort: 'medium'` by default. [`live-responses`]

### The Live API, measured again on 8 November (the live delegation failure)

The owner spoke "Can you make a search and find me the Kubernetes experts" into the dock; the voice answered at once with three invented names, no tool chip appeared and nothing was delegated. Six sessions (five billed, about 135 seconds in all): four with `scripts/voice/probe-middleware-body.mjs` (the middleware's own `liveSessionBody`, over the WebSocket) and two headless Chromium walks of the portal dock (fake microphone, every data-channel frame logged from inside the page). Each line is **fact (OpenAI, verified 8 November 2026)** unless tagged otherwise; sessions in brackets are the `s` field in `docs/voice/live-events.jsonl`.

- Delegation is the voice's own decision, steered only by its instructions. OpenAI's guide: "use the live prompt to guide when it should delegate" **fact (OpenAI docs)** (`/api/docs/guides/live-delegation`); the voice receives no tool list of its own. P2's voice prompt said "by calling the functions you are given" and gave a line to say per function (`search_people: "Searching people for kubernetes."`), but never said to delegate or not to invent. With it, the voice spoke that line (session time 5.8–6.8 s, starting as the user stopped) and delegated only at `offset_ms: 8800`, after finishing the line, so it was acting out the function itself [`portal-webrtc-walk`]. In the owner's session it carried on to invented names and never delegated. Over the socket the same prompt delegated in 5 of 5 turns [`mw-body-ws`, `mw-instructions-questions`], so the failure is intermittent. With the prompt `voiceInstructions` now renders ("You have no data and no tools of your own…", "Delegate at once, before you say anything about the request", "never invent names, people, results…", a list of what the backend can do), `session.delegation.created` came with the user's last word (`offset_ms` within one 200 ms transcript step of the last input delta), and the voice said only "One moment." until the result arrived [`mw-body-fixed-prompt`, `portal-webrtc-walk-fixed`].
- `session.client.data_channel` exists only for WebRTC. On the primary WebSocket, `session.start` with it is refused before anything is billed: `error { code: 'invalid_value', param: 'session.client.data_channel', message: 'client.data_channel is only supported for WebRTC sessions.' }`. A socket probe of the mint body must drop `client` [`mw-body-as-minted`].
- The data-channel allowlist filters as configured. With P2's `allowed_server_events`, the browser received only `session.started`, transcript deltas, `session.delegation.created`, `session.usage.updated`, `session.closed`, `error` and `response.event` carrying `response.created`, `response.output_item.done` and `response.completed`. It received no output-audio frames, no argument deltas and no `response.in_progress`. `response.item.create` and `response.create` sent on the data channel were accepted and continued the delegation [`portal-webrtc-walk`].
- The backend may call again in its continuation. After a result, the continuation can emit an `output_text` message and then a second function call in the same delegation (`search_people` again with `limit: 10`), so a delegation can take several result rounds. Reasoning items (`type: 'reasoning'`, `encrypted_content`) also arrive as `response.output_item.done` and are not calls [`mw-instructions-questions`].
- Closing during a delegation. After `session.close`, the session refuses further client events with `error { message: 'The session is closing and cannot accept new client events.', client_event_id }`. With a delegation in flight at hang-up, `session.closed` did not arrive within the dock's 5-second wait. The provider session still ended when the peer connection closed: a hangup a minute later answered `404 session_id_not_found` [`portal-webrtc-walk-fixed`].
- An output without its continuation ends the session's usefulness (G59, measured 9 November, `scripts/voice/probe-realtime.mjs live-unresolved`, one session each way). With the first call answered by `function_call_output` and no `response.create`, the next spoken request got no input transcript and no delegation in the 11 s before the cap; with the `response.create` sent, the same request was transcribed in 1.7 s and delegated in 3.8 s. Every round is continued, a stopped one included (`docs/voice-navigator-gaps.md` G59) **fact (probe)**.

### Delegation context growth, measured 9 November (G53)

The delegated Responses model re-reads the whole conversation on every response, so its input grows through a session. Measured from the sideband `usage` rows of vs_d69bbb23 (orgiq, 393 s, 59 responses; cumulative rows at most every 30 s, so each figure is the average over its interval): **9,869 input tokens per response over the first five, then 11,661, 13,124, 14,288, 15,904, 17,706, 19,458, 20,927, 22,014, 23,080 and 23,684 for the last** (about 260 more per response); 990,144 input tokens in all, 966,160 of them cached (97.6 %), 7,128 out, $0.33 for the session. The 01:42 session (vs_900938ca) started at 9,208 for its first response. The Logging record shows the figure: an "Input per response" fact (first → last interval) and an "Input / response" column on the events table's usage rows (`voiceLogModel.ts` `tokensPerResponse`).

What the Live API offers to bound it, read 9 November from the Live reference (`/api/reference/resources/live`) and the live-conversations, live-delegation and live-prompting guides:
- The voice engine's own context is managed: 128,000 tokens, summarised in the background, and past 90 % a replacement engine starts with the instructions and up to 8,192 tokens of history **fact (OpenAI docs)**. Nothing says the delegation shares this.
- `delegation.responses` takes `model`, `instructions`, `tools`, `tool_choice`, `parallel_tool_calls`, `max_output_tokens`, `service_tier`, `reasoning` and `text` (all updatable by `session.update`); none bounds input, and there is no `truncation`, `previous_response_id`, `context_management` or input cap for a delegation **fact (OpenAI docs)**.
- The input-item union `response.item.create` accepts includes `compaction_trigger` ("Compacts the current context. Must be the final input item.") **fact (OpenAI docs)**, but nothing documents what it does inside a Live delegation, and finding out needs billed sessions. **Not applied**: the dock sends tool results through `response.item.create`, and an undocumented item there could end a delegation mid-request.
- Client delegation ("you choose exactly which history … each backend request receives") would bound it, but the portal would run its own Responses calls: an architecture change, not a setting.

**Finding: with the documented settings the delegation conversation cannot be bounded today**, so `middleware/src/lib/voice/openai.ts` sets nothing new. What keeps it in check is on our side: compact results and a single page note (G31), at most four calls per user turn (G43), one page per request (G51), and fewer wasted rounds (G46–G50). At 97.6 % cached the growth costs little; it is latency and the 128 k ceiling a long session would meet that matter. Revisit when the reference documents `compaction_trigger` for delegations.

### What this changes for P2/P3

- P2 mint body: `POST /v1/live/sessions { session: { model: 'gpt-live-1', instructions, audio: { output: { voice } }, delegation: { type: 'responses', responses: { model: 'gpt-6-luna', instructions: <backend prompt>, tools: <catalogue as { type: 'function', name, description, parameters, strict: true }>, tool_choice: 'auto', parallel_tool_calls: false } }, client: { data_channel: { allowed_client_events, allowed_server_events } } }, transport: { type: 'webrtc', sdp } }`; it returns `{ sdp: transport.sdp, voiceSessionId: session.id }`, and there is no secret to hand the browser.
- P2's voice instructions must tell the voice to delegate (§1, 8 November): the delegation block alone does not make the voice delegate.
- P2 must send `allowed_client_events` without `session.update` and `session.instructions.append` (the probe's list: `session.close`, `session.input_audio.mute`/`unmute`, `response.item.create`, `response.create`, `session.thinking.append`, `session.commentary.append`). That is what makes §2's "the browser cannot change the tool list or the instructions" true.
- P2 metering: hold at least 15 seconds per mint; settle from `session.closed.usage.seconds` (cumulative, never summed) plus the delegated tokens from each nested `response.completed.response.usage`, priced as a `gpt-6-luna` call. The middleware can read both itself over the sideband (`/v1/live/sessions/{id}/attach`) instead of trusting the browser's figure.
- P2 reaper: `POST /v1/live/sessions/{id}/hangup` (200, empty body) ends a session whatever state it is in.
- P3 switches on these events: `session.started`; `session.input_transcript.delta` and `session.output_transcript.delta` (`delta`, `start_ms`, `end_ms`); `session.delegation.created` (executing begins; `target: 'responses'`); `response.event` with `event.type === 'response.output_item.done' && event.item.type === 'function_call'` (read `call_id`, `name`, and `arguments` as a JSON string; not the arguments-done event, which lacks `name`); nested `response.completed` (`output` is always `[]`); `session.usage.updated`; `session.closed`; `error` (match `client_event_id`).
- P3 tool result: `response.item.create { event_id, item: { type: 'function_call_output', call_id, output: JSON.stringify(<shaped result>) } }` for every pending call of the delegation, then exactly one `response.create { event_id }`.
- P3 phases: no thinking event exists, so `thinking` runs from the last input transcript delta to the first output transcript delta or `session.delegation.created`; `speaking` follows output transcript deltas or remote-track energy, never output-audio frames. Expect one short spoken acknowledgement and then silence during a tool, so the dock, not the voice, must show progress for slow tools (`start_computer`).
- P3 context: page-state updates go as `session.thinking.append { delegation_id: null }` (silent) or `session.commentary.append { delegation_id: null }` (spoken). Never send a delegation id under Responses delegation, and leave `session.instructions.append` to the server.

## 2. The shape

- **decision** The browser runs the tools. The voice session's function calls are executed by the portal, in the user's tab, through the same `fetch` calls, gateway socket and compute context a click would use, with the session cookie and the realtime token the tab already holds. The middleware's only new job is to mint the voice session (§6) and to meter it (§7). Reasons: every tool then inherits exactly the Cedar gate and tenant scope of the button it stands in for (there is no second authorization path to keep in step); chat and presence can only be sent from the browser today, since the server has no "post as the user" primitive (§1); navigation, `openShell` and the toast host are browser state; and the OpenAI data channel terminates in the browser anyway, so a server-side executor would need its own copy of every event. The cost is that a tool result must be shaped in the browser before it goes back to the model, which is where the injection boundary lives (§6).
- **decision** One session per tab, started and stopped from the dock, never auto-started. It survives route changes because the dock lives in the shell (`Layout.tsx`), outside the page tree. A tenant switch ends it: the tools' tenant is the session's tenant at mint time, and the portal's "entering another workspace fully leaves this one" rule applies to the voice too.
- **decision** The API key stays in the middleware. `POST /api/voice/sessions` takes the SDP offer and returns the SDP answer, exactly as `server.mjs` does, with the instructions, the tool catalogue and the voice chosen server-side. The browser never sees `OPENAI_API_KEY` and cannot change the tool list or the instructions.
- **decision** Tools are the catalogue in §4 and nothing else. There is no generic "call this API" tool and no free-text shell. Anything the catalogue cannot express the assistant says it cannot do and offers the nearest page.
- **decision** The model may act without asking for reads and navigation; it must ask before anything that spends money, runs on a machine, or reaches other people, and the dock shows the pending action as a card with Confirm / Cancel (§5). Confirmation is by voice ("yes") or by click; the tool result records which.
- **decision** `chatgpt-live-voice/` is retired once package P2 lands: `server.mjs` is replaced by the middleware route, `index.html` by the dock. The folder is deleted, not moved into `portal/prototypes/`; the README's facts are carried into this document (§1) and the `.env` key goes into `middleware/.env` as `OPENAI_API_KEY`.

## 5. The dock

- **decision** A new `@connorhoehn/ui-components/voice` entry with three primitives, added to the library first (frontend discipline): `VoiceDock`, `VoiceActivityRing`, `VoiceTurnStrip`. The portal composes them in `SocialFooter` beside the huddle half, orgiq and social tenants first, behind the `voiceNavigator` feature flag (`lib/features.ts`).
- `VoiceDock` props: `phase: 'off' | 'connecting' | 'listening' | 'thinking' | 'executing' | 'speaking' | 'confirming' | 'ended' | 'unavailable'`, `level: number` (0..1, the microphone), `outputLevel: number` (0..1, the assistant's audio), `elapsedSeconds`, `budget: { usedUsd, holdUsd } | null`, `pending: { title, detail, onConfirm, onCancel } | null`, `lastLine: { role: 'you' | 'assistant', text } | null`, `onStart`, `onStop`, `onMute`, `muted`, `unavailableReason?: string`, `compact?: boolean`, `className`, `'data-testid'`. It renders a `HuddleBar`-shaped row: the ring, the phase label (`StatusPill` tones: listening = success, executing = info, confirming = warning, unavailable = muted), the last transcript line truncated, the budget meter (`DotMeter`), mute and hang-up (`IconButton`), and the pending card as a popover above the row (`Drawer` is too heavy; a `Popover` anchored to the row, which exists in `shared`).
- `VoiceActivityRing` props: `level`, `outputLevel`, `phase`, `size?: 'sm' | 'md'`, `label`. The "it is active" visualization: a ring whose stroke width follows `level` while listening, pulses on `outputLevel` while speaking, rotates while thinking or executing, and sits still and dim when off. SVG with the library's tokens; no inline styles in the portal (the component owns its CSS).
- `VoiceTurnStrip` props: `turns: Array<{ id, role, text, at, toolCalls?: Array<{ name, status: 'running' | 'done' | 'refused' | 'failed', summary }> }>`, `maxVisible?`, `onClear`. An optional transcript strip that opens above the footer in the same slot the huddle chat uses (`useSidePaneHost`), so the user can read what was said and what ran.
- Phase rules: `listening` after `session.started`; `thinking` from the first `session.output_transcript.delta`-less pause after the user's transcript ends (the API sends no thinking event; between the last input transcript delta and the first output transcript delta or `session.delegation.created` only silent output-audio frames arrive, 100–314 ms in the probe, so the dock infers it from input end until output or delegation starts, **fact (OpenAI, verified 8 November 2026)**); `executing` while a tool call is open; `speaking` while output transcript deltas arrive or the remote audio track has energy; `confirming` while a pending card is shown; `unavailable` when the middleware answers 503 for `POST /api/voice/sessions` (no key, no budget, no grant), with the reason as the pill's title.
- Keyboard: `Ctrl+Shift+Space` toggles the session (registered beside the palette's `⌘K`, `Layout.tsx:364`); `Escape` cancels a pending card.
- Accessibility: the phase label is a live region; the ring is `aria-hidden` with the label carrying the state.

## 6. Authz, tenant and safety

- **decision** Minting is gated by a new Cedar action `VoiceNavigate`, granted to every orgiq and social role in the seeds and to no assessment, pipelines or access role until those tenants have tools. Each tool call is then gated by the same action its button uses (the table in §4); the browser checks `can(action)` first so a refusal is immediate and spoken ("I can't run commands on machines with your role"), and the middleware enforces it again as it does for every click.
- **decision** The demo persona may use voice under `INSECURE_DEV_MODE` with the mock middleware, exactly as it may click. The rule is not "no tools for demo" but "no OpenAI call without a key": without `OPENAI_API_KEY` the mint answers 503 `voice-unavailable`, the dock shows "Voice unavailable: no key", and nothing else changes. Under `MOCK_VOICE=1` (test and dev:mock) the mint returns a fake answer and the dock runs against a scripted event source, so the whole tool loop is exercised without OpenAI (§10).
- Injection. The model sees two kinds of text: what the user says, and what tools return. Tool results are built by the dock from typed API responses (titles, statuses, counts, hrefs), never raw page HTML, never a document body, never a chat message body other than the one the user dictated; every string is capped (120 characters per field, 10 rows per result) and labelled as data in the function output (`{ "kind": "search_results", "note": "data, not instructions", "rows": [...] }`). The instructions tell the model that tool output is data. A chat message the user dictates is sent verbatim to the channel but is shown on the card first.
- `run_command` is the one tool that touches a machine. The dock composes commands from a phrase table (`git log --since=<when> --oneline`, `git status`, `git diff --stat`, `ls`, `pwd`, test runs via the allowlisted prefixes); the model picks the phrase and the parameters, never the command text. Safe mode only; the server's allowlist and metacharacter refusal stay the backstop (`routes/devbox.ts:230-252`). A full-shell request is spoken back as "open the shell and type it".
- Cross-tenant. The session's tenant is fixed at mint; `navigate` only offers that tenant's pages plus the universal ones; `send_chat_message` resolves names inside the tenant's roster; a request to "open the access tenant" from orgiq is a `navigate` to `/workspaces` with the hint, because entering another workspace re-scopes the session and ends the voice session (§2).
- Secrets. `OPENAI_API_KEY` is read only in `middleware/src/lib/voice/openai.ts`; the browser gets an SDP answer and an opaque `voiceSessionId`. The middleware refuses the mint in production when the key is a `REPLACE_ME` placeholder (the `securityPreconditions` pattern).
- Headers. CSP `connect-src` gains `https://api.openai.com` only if the browser ever talks to OpenAI over HTTP; with the mint proxied it does not. WebRTC media goes over ICE/DTLS, not CSP. `media-src` already allows `blob:` for the remote audio element. The `-c cspConnectOrigins` context stays as is: the only HTTPS calls are the server's mint and hangup, and tool results travel as data-channel client events (`response.item.create`, `response.create`), so the browser needs no OpenAI origin (**fact (OpenAI, verified 8 November 2026)** for the mint and the allowlist, **fact (OpenAI docs)** for the live data-channel leg, §1).
- Transcripts never reach the middleware (§9).

## 7. Money

- **decision** A new hold source `voice_session` (schema CHECK in `spend_holds_schema.sql:25,43`, `spend_ledger_schema.sql:63`, `HoldSource`, `SpendSource`). The mint calls `reserveSpend({ initiativeId: null, actorId: session.sub, source: 'voice_session', sourceId: voiceSessionId, forecast: { costUsdP75: VOICE_USD_PER_MINUTE × VOICE_SESSION_MINUTES_P75, costUsdP25: ... , confidence: 'prior' }, expiresInMs: VOICE_SESSION_MAX_MINUTES × 60_000 + HOLD_GRACE_MS })`. Defaults: `VOICE_USD_PER_MINUTE=0.05` (the README's third-party figure; a config value until the price list says otherwise), p75 10 minutes, max 30 minutes. A refusal is spoken as the dock's `unavailable` reason ("Your budget is used up for today").
- Settlement. `session.usage.updated` carries `usage.seconds`; the dock posts it on close (`POST /api/voice/sessions/:id/close { seconds }`) and the middleware writes one `recordSpend` row (`costUsd = seconds / 60 × rate`, `costBasis: 'estimated'`, `provider: 'openai'`, `model: LIVE_MODEL`) that settles the hold. A session that never closes (tab killed) is swept by a reaper after `VOICE_SESSION_MAX_MINUTES + grace`: it calls `/v1/live/sessions/{id}/hangup` as `server.mjs:133` does, and books `unknown`, never 0.
- Cut-off. The dock shows the budget meter from the hold; at 90% it says so ("two minutes left on this session"); at 100% the dock sends `session.close` itself. The middleware reaper is the backstop.
- Tool spend. The catalogue's tools spend nothing except `start_computer`, whose box takes its own holds through the existing devbox path; the voice session is not charged for it.
- `provider` gains `'openai'` in the ledger's provider list if it is a CHECK (read `spend_ledger_schema.sql` at build time).

## 9. Data model and logging

- New table `voice_sessions` (`id TEXT PK`, `tenant`, `actor_sub`, `hold_id UUID REFERENCES spend_holds`, `provider_session_id TEXT`, `model`, `started_at`, `closed_at`, `seconds INT`, `cost_usd NUMERIC(10,4)`, `cost_basis`, `stop_reason TEXT`, `tool_calls INT`), RLS and role grants as the other tenant tables.
- New table `voice_tool_calls` (`id`, `voice_session_id`, `at`, `name`, `args_sha256 TEXT`, `outcome TEXT CHECK IN ('done','refused','failed','cancelled')`, `confirmed_by TEXT`, `duration_ms`). Arguments are hashed, not stored: a search query or a dictated message is the user's business; what is kept is which tool, whether it was allowed, and how long it took.
- Stored nowhere: audio, transcripts, the model's words, the user's words. The browser keeps the transcript strip in memory for the session and drops it on close; "copy transcript" is a browser-side action.
- Logged by the middleware: the mint (actor, tenant, hold id, provider session id), the close (seconds, cost), each tool-call row; never the arguments. The portal logs nothing to the server beyond those rows.
- Metrics (`emitFleetMetric` style): `voice-sessions-started`, `voice-session-seconds`, `voice-tool-calls{name,outcome}`, `voice-unavailable{reason}`.
