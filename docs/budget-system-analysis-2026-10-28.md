# OrgIQ agent budget system: honest analysis (2026-10-28)

**Continuation checkpoint (2026-10-28):** the analysis below records the earlier
state. The baseline ledger/schema work is now deployed; the local DE-32 batch
adds configurable Claude estimates and a direct agent-project-run writer.
Reported/estimated provenance is retained through project settlement, bot
ownership and job backfill. BFF Bedrock metering, direct-run historical backfill
and mock-ledger parity, user budgets, holds, a funded maintenance reserve and
billed reconciliation remain follow-ups. Local validation and the rollout order
are recorded in `local-backlog-goal-2026-10-28.md`.

**Executive summary**

1. Money is modelled as a monthly per-initiative allocation plus per-SME sprint envelopes, with burn derived at read time from `bot_runs.cost_usd`; only `POST /api/bots/dispatch-work` runs the full gate set, and every money gate on it is a confirmable 409 that fails open when its inputs are missing.
2. Four paths spend Bedrock money with no budget gate and (before the uncommitted DE-30 ledger) no budget visibility: ad-hoc box tasks, platform-api's agent loop, queued work jobs, and direct `POST /api/agent-projects/:id/runs` — the last one is still unmetered even with the ledger on, and no DE spec names it.
3. No dollar in the system comes from Bedrock's bill: Claude Code's self-reported `total_cost_usd` (its own price list) is recorded as "reported", Nova agent traces are priced token×table into observability only, and every Claude profile prices to `null`; the account-wide AWS Budget is the only true-bill signal.
4. The uncommitted DE-30 work is sound in shape (append-only, unknown ≠ zero, idempotent key, dual-read drift log) but is best-effort on write, defaults to `off`, writes no `grant_id`, and is not applied to Aurora.
5. Against the intended model (real dollars, user budgets, boxes and jobs covered, a funded maintenance floor, discretionary remainder driving dispatch), the DE-30..53 set covers metering and initiative-level enforcement but has nothing for user budgets, nothing for billed reconciliation, and DE-39/DE-36 as written would starve the maintenance floor rather than fund it first.

## 1. The model as built

**Allocation.** `initiative_budgets` is one row per initiative, `allocated_usd`, `period` locked to `'monthly'` by CHECK (`schema/agent_budgets_schema.sql:14-21`). Spend is never stored; the header says it is derived from `bot_runs.cost_usd` through the three-way attribution (`:4-8`). Written by `PUT /api/budgets/:id` behind `ManageBudgets` (`middleware/src/routes/budgets.ts:24,51`), held by hr-admin, org-leader and program-owner Cedar roles.

**Grants.** `budget_grants` is (initiative, optional sprint, grantee person, `allocated_usd`) (`schema/program_schema.sql:43-57`); a null `sprint_id` is a standing grant (`:46-47`). Written behind `ManageBudgets` (`routes/grants.ts:26,58,100`). A grant is "active" when its sprint is `active` or it has no sprint (`lib/bot-runner.ts:544-546`).

**Attribution to an initiative** is `spendPredicateSql` (`providers/budgets.ts:117-128`): `cost_usd IS NOT NULL AND (run's work item ∈ initiative OR bot targets initiative OR bot targets a codebase delivering it)`. The Projects rollup carries its own copy (`providers/projects.ts:492-497`). In ledger mode the entry's `initiative_id` was resolved once at write time by `COALESCE` over the same three arms in order (`providers/spend-ledger.ts:148-152`).

**Attribution to a person** is `bot_runs.dispatched_by` (`schema/agent_run_attribution_schema.sql:32`), set from the session on dispatch-work (`lib/bot-runner.ts:1303-1307`) and manual bot runs (`routes/bots.ts:785`), null for cron and PR-watch (`lib/bot-runner.ts:920-925`). Envelope burn = `SUM(cost_usd)` of runs where `dispatched_by = session.sub`, inside the sprint window, attributed to the initiative (`providers/bots.ts:308-345`). In ledger mode it becomes `SUM(cost_usd) WHERE actor_id = :by AND initiative_id = :pid` (`:332-337`), which also counts box tasks and jobs the person caused.

**Windows.** Allocation spend is calendar month, `PERIOD_START_SQL = date_trunc('month', NOW())` (`providers/budgets.ts:105`), used by the per-initiative CTE (`:488-500`), org totals (`:879-885`), by-model/by-trigger (`:909-929`) and the Projects rollup (`providers/projects.ts:497,750-753`). Envelope burn is `[sprint.starts_on, ends_on + 1 day)` (`providers/bots.ts:322-329`). The maintenance floor view `v_initiative_maintenance_30d` is trailing 30 days, cron-triggered, bot-target arms only (`schema/program_schema.sql:89-104`), while the Budgets page's `maintenance_usd` is the cron subset of month-to-date spend over all three arms (`providers/budgets.ts:493-494`). Per-bot daily caps use `date_trunc('day', NOW())` (`providers/bots.ts:192-196`). So the allocation, the floor it is "read against", and an SME's envelope each use a different window; nothing aligns them (DE-38 is the fix).

**Read tier.** Dollar fields are withheld (never zeroed) below `BUDGET_READ_ROLES` or the `budgets-reader` capability (`lib/budget-read-tier.ts:24,34-39,63-68`).

## 3. Enforcement gaps

- **Fail-open.** No allocation row → no brake (`routes/bots.ts:317`, `lib/bot-runner.ts:340`). No active grant → no brake (`:355`). `loadEnvelope` catches every error and returns null (`lib/bot-runner.ts:639-644`). `getBudget` goes through `safeExec`, which turns a missing table into no rows (`providers/budgets.ts:454-462`). The attribution column missing degrades the envelope to "refuse only a forecast bigger than the whole envelope" (`lib/bot-runner.ts:474-481`). Only the grant gate fails closed (`:777`, `routes/bots.ts:252-255`).
- **Confirmable-only.** All three money brakes are 409 + flag; `confirmed` short-circuits `decideAllocation` and `decideEnvelope` before any arithmetic (`lib/bot-runner.ts:340,461`). The deprecated `confirmOverBudget` still opens two gates at once (`routes/bots.ts:180-186`). Nothing is non-overridable (DE-36).
- **Races.** dispatch-work reads the budget (`routes/bots.ts:317`) and starts the run (`:391`) with nothing written between; spend appears only after the run finishes and the 30 s reconcile copies it (`lib/bot-scheduler.ts:27,142`), so N concurrent dispatches on one initiative all see the same remainder (DE-34). The boot catch-up fires every stale cron bot in one loop (`lib/bot-scheduler.ts:131-139`) with the same blindness. The concurrency ceiling's `INSERT … SELECT … WHERE COUNT(*) < :ceiling` (`providers/bots.ts:1082-1094`) is not serialised under READ COMMITTED; its "TOCTOU-safe" comment is wrong (DE-37).
- **Unknown cost.** The predicate's first clause drops null-cost runs (`providers/budgets.ts:119`); a Bedrock run that reports no figure spends no allocation and no envelope. The ledger records `cost_basis='unknown'` and the readers count it (`:556`), but nothing outside `providers/budgets.ts` reads `unknownCostCount` (grep) — no brake, no UI. SDLC `max_cost` returns no gate on null (`lib/sdlc-policy.ts:200`), and the reviewer that then approves is Nova (DE-33).
- **After-the-fact.** Over-budget is a flag: `overRunBudget` on the outcome (`lib/bot-runner.ts:1684-1693,1792-1799`), only for bots with `budget_per_run_usd`; the marketplace's `budgetPerRunUsd` is never persisted (`routes/bots.ts:391-397` passes no cap), so the flag cannot fire for those runs. No mid-run meter exists; `appendEvent` only accrues on `result` (`lib/devbox-fleet.ts:550-567`) (DE-35).
- **Global vs per-initiative.** One global `BOT_MAX_CONCURRENT=3` (`lib/bot-runner.ts:203-206`), counting bot_runs only (`providers/bots.ts:1177-1200`); jobs and box tasks are bounded by idle boxes and the box busy flag. Per-bot daily caps, none per initiative or per person (DE-37). No per-user budget concept exists anywhere in `middleware/src` or `schema/` (grep for user/personal budget: none).
- **Unattributed spend has no gate.** A `ManageDevbox` holder can queue free-text jobs and run tasks on an initiative-less box indefinitely; in ledger mode these land `initiative_id = NULL` and count only in org totals (`providers/budgets.ts:553,949-961`), braked by nothing.

## 4. Correctness and honesty of the numbers

- **Three-arm OR over-counts.** A run whose work item sits in initiative A, dispatched by a bot targeting initiative B, matches both `spendPredicateSql` calls, so per-initiative rows can sum to more than the org total (which is an unattributed `SUM(bot_runs)`, `providers/budgets.ts:879-885`). The ledger books it to the first arm (`providers/spend-ledger.ts:148-152`); the dual-read mode will log the resulting drift as a mismatch (`providers/budgets.ts:590-606`), so expect noise that is correct, not a bug.
- **"Reported" is not billed.** Every box, bot and job dollar is Claude Code's `total_cost_usd` (`lib/devbox-runner.ts:203`, `lib/devbox-fleet.ts:555`). `lib/run-cost.ts:20-30` documents that this figure is Claude Code's own first-party price list (it priced a loopback Qwen run at Sonnet list price). On Bedrock it is probably close, but nothing checks it; the ledger labels it `reported` (`providers/spend-ledger.ts:58-61`), which overstates its provenance.
- **Unpriced Claude.** `BEDROCK_PRICING` has four Nova/Titan rows (`lib/pricing.ts:19-24`); `estimateCost` returns 0 for unknown ids (`:38-40`), `estimateCostOrNull` returns null (`:82-85`). The devbox default and allowlist are all `us.anthropic.claude-*` profiles (`infra/lib/devbox-stack.ts:105,250`), so every lab trace prices null and no fallback estimate exists when Claude Code omits a figure. Cache-read/cache-write tokens, which dominate a Claude Code run (`lib/devbox-fleet.ts:454-479`), have no price slot (DE-32).
- **Observability cost sums null as zero.** `routes/cost.ts:103-104,165-167` use `COALESCE(total_cost_usd, 0)` inside `SUM`, the exact "confident zero" the rest of the tree argues against; it reports `with_cost` beside it, so it is recoverable but easy to misread.
- **Maintenance floor disagrees with itself.** The view is 30-day trailing on bot-target arms; the Budgets page's `maintenance_usd` is month-to-date on all three arms (section 1). The operating model says to read an allocation against the floor; the two figures a release manager can see for "the floor" use different windows and arms.
- **Envelope burn is partial by construction.** Cron, PR-watch and pre-migration runs count against nobody (`providers/bots.ts:296-301`), while they do count against the initiative allocation. In ledger mode an SME's envelope also burns for box tasks and jobs that no envelope brake ever judged.
- **Mock vs Aurora.** The mock derives bot-run spend from the `bot_runs` fixture and stores only ad-hoc entries (`mock/spend-ledger.ts:12-19`, seeded empty); it has no job queue, so the `job` writer and `unlessBotRunOwnsJob` guard are Aurora-only (`providers/spend-ledger.ts:81`); `runCostSamples` returns null offline so every mock forecast is a prior; `mock/devbox-fleet.ts:107-213` hard-codes `spendUsd` per box, a stored aggregate the mock floor forbids (DE-31). The seeded cron history carries `dispatchedBy: null`, so no envelope burns offline until a dispatch happens.
- **What the release manager sees.** `/admin/budgets` columns: Initiative, Allocated, Spent, Remaining, Runs, Last activity, Updated by (`portal/src/pages/budgets/InitiativesReport.tsx:322-409`). No unknown-cost count, no in-flight or reserved money, no per-person line, no box or job spend until `SPEND_LEDGER=ledger`, and "Remaining" is allocation minus settled spend only.
- **What the SME sees.** `GET /api/sprints/envelopes` returns their own dispatched burn with `attributionAvailable` and the explicit note that cron and other people's runs are excluded (`routes/sprints.ts:182-195`); initiative dollars are "Locked" below the tier (`lib/budget-read-tier.ts:34-39`). They cannot see what a job or box task of theirs cost.

## 6. Gap to the intended model

The intended model: (1) real Bedrock dollars, (2) budgets on users, (3) reporting over all of it, (4) boxes and jobs covered, (5) the maintenance floor funded first, (6) the discretionary remainder drives dispatch. For each: today, what the specs cover, what nothing covers, smallest build.

**1. Budgets are real money, metered from Bedrock.**
*Today:* nothing reads Bedrock's bill. Sources are Claude Code's self-report (`lib/devbox-runner.ts:203`), token×static table for Nova agents and judges (`lib/trace-sink.ts:1114-1125`), null for Claude profiles (`lib/pricing.ts:82-85`), and route-decided $0 for local (`routes/local-compute.ts:669`). The only true-bill artefact is the account-wide AWS Budget at 80/100/120 % (`infra/lib/observability-stack.ts:274-310`), account grain, not per initiative or user.
*Specs:* DE-32 adds Claude rates from SSM and an `estimated` basis; DE-30 keeps `cost_basis`; DE-33 defines unknown. All three produce better estimates, not billed figures.
*Nothing covers:* a `billed` basis, or any reconciliation of estimates against what AWS charges.
*Smallest build (inferred, AWS-native, not verified in this tree):* route every Claude Code and agent invocation through a Bedrock **application inference profile** per cost centre (one per initiative, optionally per user), tagged `orgiq:initiative` / `orgiq:user`; the devbox already takes `--model` as a profile id (`agents/devbox/main.py:86-110`), so this is a model-id change plus IAM on the profile ARNs (`infra/lib/devbox-stack.ts:130-139` already allows `inference-profile/*anthropic*`). Then a nightly reconciler reads Cost Explorer grouped by those tags (≈24 h delay), writes `spend_reconciliations (cost_centre, day, billed_usd, ledger_usd, drift)` and a per-period true-up row with `cost_basis='billed'` into `spend_entries`. Enforcement stays on estimates in real time; the report shows billed vs estimated per initiative and alarms on drift >10 %. DE-32's price table is still needed for the real-time half. Decision owed: profile granularity (initiative only, or initiative×user; there is an account limit on application inference profiles) and whether true-up adjusts the current period or is a separate line.

**2. Budgets apply to users.**
*Today:* no user budget exists. The nearest things are `budget_grants` (person × initiative × sprint, `schema/program_schema.sql:43-57`), `dispatched_by` on runs, and `actor_id` on ledger rows (`schema/spend_ledger_schema.sql:26`). Enforcement against a person happens only inside one initiative's envelope on dispatch-work (`routes/bots.ts:355-378`).
*Specs:* DE-31 adds a read-only `GET /api/me/spend` and a per-actor rollup; DE-34's lock is initiative-then-grant; DE-36 caps initiatives and grants. None caps a user across initiatives.
*Nothing covers:* a per-user allocation and cap, enforced on every path.
*Smallest build:* `user_budgets (user_id PK → app_users, period, allocated_usd, hard_cap_usd, set_by, …)` (additive, both loaders); `decideUserBudget({ allocated, cap, spent, held, p75 })` pure; the actor burn is `SUM(cost_usd) FROM spend_entries WHERE actor_id = :sub AND occurred_at >= period`, which the ledger already supports (index at `schema/spend_ledger_schema.sql:42`). Evaluate it inside DE-34's `reserveSpend` as a third advisory lock (`'user:' || sub`, taken after initiative and grant) so it covers every path that takes a hold; add `userBudget` to the 409/403 body shapes. Write path behind `ManageBudgets`; a user never raises their own. Decisions owed: default allocation for a user with no row (proposal: none, unbraked, shown as blind spot like initiatives), whether the user cap is a ceiling across all initiatives in addition to envelopes (proposal: yes, both apply), and whether cron spend ever charges a user (proposal: never; it charges the floor, item 5).

**3. Reporting and metrics on all of it.**
*Today:* four surfaces that never meet — Budgets page per initiative (`InitiativesReport.tsx:322-409`), envelopes per person×initiative (`routes/sprints.ts:195`), `routes/cost.ts` for agent traces, the fleet chip per box (`lib/devbox-fleet.ts:565-567`). No burn rate, no projection, no model or actor breakdown that spans sources; the org summary has by-model and by-trigger for bot runs only (`providers/budgets.ts:909-929`, ledger twin `:958-961`).
*Specs:* DE-53 (initiative report with forecast, reserved, envelopes, run outcomes), DE-31 (per-actor rollup), DE-50 (CloudWatch metrics and threshold alarms).
*Nothing covers:* one grouped read over the ledger by actor × initiative × model × source × trigger with a burn rate, nor billed-vs-estimated (item 1), nor user-budget remaining (item 2).
*Smallest build:* `GET /api/spend/report?groupBy=initiative|actor|model|source|trigger&period=` over `spend_entries` returning `{ knownUsd, unknownCount, entries, burnPerDay7d, projectedPeriodEndUsd }` per group, plus `remaining` when the group has an allocation (initiative or user). One `DataTable` with a group selector on `/admin/budgets`, and DE-53's initiative view reuses the same read filtered to one initiative. **4. Budgets apply to boxes and queued jobs.**
*Today:* with the uncommitted DE-30, box tasks, the agent loop and jobs are *recorded* (`routes/devbox.ts:639-649`, `routes/internal-devbox.ts:240-261`, `lib/job-dispatcher.ts:71-84`) but none is *gated*: `InvokeRuntime` goes out before any budget read (`routes/devbox.ts:574`), the dispatcher claims whatever is queued for every idle box (`lib/job-dispatcher.ts:166-174`), and a job with no initiative needs no grant (`lib/initiative-scope.ts:153`). *Specs:* DE-34 takes holds for promote and `/api/work/jobs` but defers box tasks; DE-36 caps every hold path; DE-37 gives box tasks a slot; DE-50 adds a pause at `runTaskAndForward` and the dispatcher tick.
*Nothing covers:* box tasks in the hold (left as a decision), direct agent-project runs anywhere, unattributed jobs.
*Smallest build:* one chokepoint, `assertAndReserveSpend({ initiativeId, actorId, grantId, p75, source })`, which is DE-34's `reserveSpend` plus the user lock from item 2, called at exactly five places before any side effect: dispatch-work (`routes/bots.ts:391`), `fireBot` before `markBotRan` (`lib/bot-runner.ts:991`), the dispatcher between `claimNextJob` and `markRunning` (`lib/job-dispatcher.ts:96`; refuse puts the job back to `queued` without burning an attempt), `runTaskAndForward` before `InvokeRuntime` (`routes/devbox.ts:574`), and `dispatchGovernedRun` (`lib/sdlc-pipeline.ts:56`) so direct agent-project runs are covered without a sixth call site. Box tasks hold the model prior p75 (box `projectId` → initiative; actor always known on both routes). **5. Necessary bots always have a reserved allocation.**
